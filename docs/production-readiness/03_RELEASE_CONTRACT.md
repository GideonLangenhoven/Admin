## A. Universal rules — every agent reads this section

**A1 — Preserve legitimate customers.** Keep business, administrator, Auth-user, booking, customer, voucher, invoice and provider-reference identities intact. No database reset, customer recreation, blanket password reset, historical payment replay, or destructive migration as a shortcut. Existing customers must not re-onboard. Intentional security restrictions may change unauthorized behaviour, with clear owner communication and recovery.

**A2 — Preserve authorization.** Identity, role/action permission, and tenant/object ownership are separate checks. Request headers, hostname, subdomain, cookies, localStorage and model output do not establish private permission. Public catalogue routing can use tenant selectors, but private access requires independently verified authority. Privileged service calls must validate original authority and every affected tenant/object. Never make a test pass by allowing cross-tenant access or disabling row-level security.

**A3 — Preserve financial truth.** No overselling, negative balances, duplicate financial posting, over-refund, unauthorized adjustment, or incorrect merchant/mode/currency. Use exact decimal/minor-unit arithmetic, database transaction invariants and stable operation identifiers. External provider effects cannot be wrapped in the database transaction: durable intent, safe retries, explicit unknown/pending states and reconciliation are required. Do not claim exactly-once external delivery without a supported provider mechanism.

**A4 — Protect the environment.** Positive non-production identification, synthetic data, and effective outbound restrictions are required for destructive/load/fault tests. A marker-labelled tenant inside production is not staging. Safeguards must reject production database IDs/hosts, production service credentials, unapproved recipients and payment modes. Verify guards with negative tests. Any production mutation, live notification, financial transaction, expensive load, new paid resource or destructive cleanup requires explicit environment/action/window/cost approval. Never expose secrets or unnecessary personal information to prompts or reports.

**A5 — Evidence is mandatory.** Distinguish source presence, unit results, real database tests, provider simulations, actual provider tests, deployed verification and load results. Fake results, skipped critical tests, stale logs, mocked delivery, globally disabled controls and weakened assertions cannot satisfy a gate. No feature removal or changed commercial/cancellation terms without explicit product approval. Keep uncertified integrations disabled.

**A6 — Preserve this branch.** Retain working read-only demo restrictions and deliberate synthetic demo behavior. Shared demonstration access must never authorize real customer changes, messages, live payments or another tenant's private data. Do not let public demo credentials become a general performance-test or administrator identity. Preserve approved pricing/onboarding rules, product branding and accessibility requirements. Test legitimate demo browsing separately from the distinct real-staff identities used for capacity qualification.

## D. Security and abuse gate

**D1 — Authentication.** Retire fast unsalted password dependence through a backwards-compatible Auth migration. High-entropy random-token hashes have different requirements from human-password storage; do not indiscriminately replace all SHA-256 uses. Reset tokens must have appropriate expiry, atomic single-use handling, secure storage, uniform public responses, safe retry recovery and trusted redirect hosts. Verify server-side session expiry/revocation and MFA enforcement for approved sensitive roles/actions, including direct APIs and RLS where relevant. Test enrollment before broad enforcement.

**D2 — Authorization and isolation.** Test all role levels, anonymous visitors, customers, active/suspended staff, active/non-trading businesses, platform administrators, and server identities. Validate every entry point, batch wrapper, RPC, public API/GraphQL surface if enabled, export and storage path. Verify tenant A cannot read/write B’s private data or inject audit events, and lower roles cannot issue refunds, mark payments or change credentials without permission. Use exact allowlists, not substring matches for powerful roles. Public pages must expose only deliberate public columns.

**D3 — Database security.** Validate TLS certificates for direct database connections; use a correct trust configuration rather than `rejectUnauthorized: false`.  Review effective table AND column grants, inherited/PUBLIC privileges, RLS policies, security-definer functions, function execution grants, constrained search paths, views, storage policies and tenant relationship constraints. Extend drift checks to these surfaces. Test using actual low-privilege identities, not only the service role. Do not blindly regenerate the security baseline; each change needs review against intended policy.

**D4 — Abuse resistance.** Rate-limit demo sign-in/date refresh without changing real customer dates.  Enforce shared limits at the actual ingress paths, including direct Edge Functions and public database/RPC routes where applicable, not only the Next.js proxy. Combine account/user/tenant and trusted-proxy IP controls as appropriate. Test shared-office IPs, distributed attempts, Redis/limiter failure, reset/email bombing, OTP guessing, fake holds, expensive chat, large batches and exports. Bound payload bytes, execution time, retries and AI/provider spend. Prohibit production test bypasses with deployment/configuration checks. Do not rate-limit verified provider webhooks like interactive logins; validate/dedupe them and test bursts separately.

**D5 — Browser/input/storage.** Parameterized queries, validated types/ranges, safe URL/redirect handling, upload-byte/type/size validation, safe previews and output encoding. Review XSS, SSRF, raw HTML/template paths, credentials leakage, CSRF appropriate to the actual cookie/bearer design, caching and clickjacking. Tighten CSP without breaking intentional embeds or integrations. Test real server responses, not just config text. CORS is not authorization.

**D6 — Supply chain and operations.** Audit actual lockfiles and deployed Node/Next/React/SDK versions against current primary-source advisories; include dev/CI dependencies where exploitable. No unresolved exploitable critical/high findings or untriaged high/critical advisories. Non-applicable findings require reachability evidence and review. Check secret scanning across relevant Git history and build artifacts, least-privilege CI/deployment access, infrastructure-owner MFA, preview-environment separation and sensitive logging. Revoke confirmed exposed credentials with a coordinated rotation plan; making a repository private alone does not revoke a leaked secret.

Use OWASP ASVS Level 2 as a coverage checklist where relevant. Do not claim formal certification from checklist completion. Expand verification when a discovered issue reveals another reachable path.

## E. Durable work and financial failure tests

**E1.** Test database commit/provider-call boundaries: crash before submission, timeout after possible provider acceptance, duplicate delivery, worker death after claiming work, lease expiry and safe reclaim, out-of-order callbacks, and failure while persisting a result. **E2.** Treat 202/pending and manual-refund-required as pending/action-required, not completed. Preserve successful provider operations when a subsequent notification fails. Store complete batch outcomes including succeeded, pending, failed and unprocessed IDs. Financial/audit records must be server-authored and attributable to validated business/caller authority.

**E3.** Bound worker batches and concurrency; use durable claiming, retry backoff/jitter and terminal-failure visibility. Test fairness so a noisy or paused tenant cannot starve active tenants. Transactional notifications must not be blocked behind marketing work. Measure both age of oldest work and total backlog. A successful HTTP cron response does not prove that its eligible work completed.

**E4.** Repair historical inaccurate logs/states with reviewed reconciliation, not automatic replay. Never mass-resend reminders for trips already completed or reissue historical refunds. Preserve consent, state, original keys and original payment modes through remediation.

## F. Definition of the 500-user workload

Do not equate accounts, browser connections, virtual users, requests, or businesses.

**F1 — Approved profile (`BT500-LAUNCH-V1`).** Qualify **500 unique authenticated operator/staff accounts and 500 simultaneously connected active sessions**. The current database enforces three staff seats per business, so distribute the accounts across167 synthetic businesses, with two accounts in the final business. This does not certify500 operator businesses. Add a separate business-fleet profile if that is the commercial target.

Each active session performs approximately one meaningful user action per10 seconds: an initial target of50 user actions/second. Model70% reads,20% legitimate writes and10% other authenticated workflow actions. Derive endpoint fan-out from browser traces; report actual measured fan-out. Do not fill the numerator with static assets or cached landing-page requests. Keep500 authenticated Realtime connections when the product requires one per active session; verify actual sockets/channels separately. Before qualification, record the real product connection topology and the resulting required connection/channel footprint in the approved workload. Do not fabricate idle sockets or silently omit required connections; any change to the agreed workload needs a new named profile.

**F2 — Companion/background traffic.** Run customer booking traffic and job work concurrently, not sequentially after dashboard load. Proposed starting load:5 public browse/availability actions/second;0.5 checkout creations/second;1.25 controlled webhook deliveries/second including tagged duplicates; and500 transactional jobs over a10-minute burst while background marketing work is active. Measure actual extra backend requests. Use isolated deterministic provider doubles for high-volume traffic and a separately approved set of genuine provider sandbox transactions. Stubbed throughput is not provider-delivery throughput. Public/guest claims cover only this stated load.

**F3 — Representative data.** Use projected12-month records and tenant skew where available. **F4 — Test sequence.** Establish low-load correctness, ramp through100,250 and500 active sessions, and sustain the full target mixed load for60 minutes. **F5 — Correctness contention.** Independently run repeated last-seat booking contention, simultaneous voucher redemption, refund retries, guest changes during payment and expiry/payment races. ## G. Proposed measured acceptance thresholds

Targets apply at the qualified steady workload, not to averages over a mostly idle ramp. Separate metrics by critical endpoint/journey so fast endpoints cannot conceal slow ones. Use stricter existing approved budgets where applicable; agree any necessary changes before qualifying runs.

| Metric | Initial requirement |
|---|---|
| Common authenticated reads | p95 <= 750 ms; p99 <= 1,500 ms |
| Application writes | p95 <= 1,500 ms; p99 <= 3,000 ms |
| Unexpected failures for valid traffic | < 0.1%, with no sustained failure pocket hidden by aggregate averages |
| Critical security/financial invariants | Zero cross-tenant private access, unauthorized effects, overselling, double financial posting, over-refunds or negative balances |
| Verified webhook acknowledgement | p95 <= 1 second from request arrival at ingress to acknowledgement after authentication and durable acceptance; invalid events rejected without mutation |
| Payment-event application | p95 <= 10 seconds after accepted event arrival under the defined test profile |
| Realtime UI update | p95 <= 2 seconds; no unrecovered disconnects at the qualified footprint |
| Transactional queue | p95 start delay <= 60 seconds; oldest eligible job <= 120 seconds in steady state |
| Burst recovery | All jobs from the defined500-job burst reach the approved terminal outcome within10 minutes after its last scheduled enqueue; overload queues recover within10 minutes after normal load resumes |
| Resource headroom | At least 30% sustained headroom on provisioned bottlenecks and relevant connection/worker quotas; no growing memory/connection leak during soak |
| Client experience | No newly broken critical mobile/desktop flows; preserve approved Web Vitals, accessibility and bundle budgets and test long lists/inbox |

These clarified timer definitions are proposed and require workload approval before qualification. Record the burst's first/last scheduled enqueue, actual admission, and completion times as well as per-job queue delay; delayed admission must not move the deadline. Define terminal outcomes so discarded or permanently failed transactional work cannot count as a successful drain. Freeze action/endpoint mappings, client-versus-server timing, error denominators and rolling failure-window criteria, resource/connection quota headroom calculations, realistic soak activity, and marketing offered rate before the first qualifying run. Unresolved definitions block qualification, not independent isolated correctness work.

Interactive payment-page human time is not an application-write latency metric. Measure real provider calls separately and include provider waits in the observed end-to-end results; do not quietly subtract slow dependencies. Report simulated versus genuine provider measures distinctly. Marketing latency and account-specific provider ceilings must be named and approved before testing; no claim of instant unlimited messaging.
