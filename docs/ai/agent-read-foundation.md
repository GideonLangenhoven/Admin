## Operation contract

All inputs reject unknown fields. The owner approved a `MAIN_ADMIN`-only pilot on 2 October 2026. The deployed disabled service requires a validated bearer token, the exact connected business, an active persisted grant, current unsuspended `MAIN_ADMIN` membership, unchanged owner consent role, and a trading subscription status accepted by the existing `isTradingStatus` helper. `OPERATOR`, `ADMIN`, `SUPER_ADMIN`, all other roles and browser-selected tenant overrides are rejected, including staff with a matching grant. Supplied tour/departure IDs are checked within the requested business. The applied migration also restricts consent roles, grant-read policy and observation checks to `MAIN_ADMIN`. The additional trusted-provider-binding check remains local.

This owner-only policy change passed 95 mocked-Auth unit tests and 29 labelled local PostgreSQL checks, targeted ESLint and focused TypeScript checks in an isolated snapshot. Its service safeguards were included in the disabled Admin source deployed on 3 October 2026 as `dpl_7Gy8PAtiUue5QERVdTkEWR29eZJS` and are preserved in the latest release. The matching SQL is now applied through migration `20261003160000`. That deployment did not include consent UI or OAuth. These are now implemented locally; actual native Auth/provider journeys remain unverified.

The timestamp is obtained before the bounded reads; this is an observation window, not an atomic multi-query snapshot or a seat guarantee. Refresh before acting through the existing booking flow. Invalid list rows produce an explicit unknown result, not a confirmed empty schedule.

### Per-person waiver policy — 3 October 2026

The owner answered “per person counts”. `outstanding_waiver_participants` replaces the earlier booking-level waiver field; payment counts retain their own booking unit. This contract change is included in the disabled Admin source and the SQL aggregate is applied; there is no released external caller. The aggregate is `STABLE SECURITY INVOKER`, checks current owner/grant/attention scope and same-business departure independently, preserves RLS, and returns only a count/null and fixed reason. The read service never selects participant payloads, names, DOBs, waiver tokens or guardian identifiers. It validates the aggregate and projects only approved fields, including if an upstream returns extra private material.

The owner also selected “All active bookings (recommended)” for payment attention on 3 October. Retain the existing non-cancelled/non-expired DRAFT/PENDING/PENDING PAYMENT/HELD/PAID/CONFIRMED/COMPLETED records where `amountOutstanding` is positive. Explicit tests cover every eligible status, fully paid records and the existing PAID/COMPLETED zero-capture legacy fallback. This does not change billing, booking eligibility or refund logic, and it is not independent payment-provider/settlement proof. Pending reschedule upgrade balances remain unknown.

Definitions: an active PENDING booking contributes its `qty`, because the current form asks for every guest before signing. SIGNED requires a finite nonfuture signing timestamp, signer name, risk acceptance and a participant array exactly matching quantity. Each entry needs a nonblank name, valid nonfuture ISO DOB and boolean liability acceptance. An explicit false acceptance contributes one outstanding person. A minor needs the existing form's recorded guardian consent/name/identifier/countersignature fields; missing evidence makes the aggregate unknown. Age uses the signing date in the business zone and the form's calendar-age rule, including leap birthdays. It does not use age at retrieval. Empty complete sets may return zero.

Legacy group signatures, quantity/array mismatches, malformed records, absent guardian evidence and unconfigured zones for signed records produce null, never a guessed zero. This is recorded acceptance coverage, not verified distinct identities, guardian relationships, independent guest signatures or legal validity. The form uses the browser's local calendar and does not store that zone; near-birthday discrepancies need review before a live claim. `sign_waiver` accepts a supplied payload without server-side participant validation, and the legacy form lacks participant entries. Both signing paths remain untouched. Production completeness/waiver-version/exemption evidence is still a launch blocker; no legacy record was backfilled or reclassified.

Actual local verification: baseline 111/111 unit tests and 40/40 PostgreSQL checks; per-person source 128/128 unit tests and 76/76 PostgreSQL checks; with explicit all-active payment cases, 138/138 unit tests. Targeted ESLint and focused strict TypeScript pass. Whole-application TypeScript passed before and after applying the per-person files. Fixtures cover three pending people, partial/complete acceptance, legacy records, minors, quantity/DOB/limit errors, fresh/stale results, owner changes, scopes, foreign tenants and a read-only transaction with no side effects. Auth is mocked; no real OAuth or platform connection was tested. The HTTP handler and disabled constant remain unchanged. The [participant deployment record](../production-readiness/evidence/AGENT_PARTICIPANT_DEPLOYMENT_20261003.json) records the earlier service source update, when SQL was still local. The [subsequent deployment record](../production-readiness/evidence/ALL_EXCEPT_AGENT_SERVICE_DEPLOYMENT_20261003.json) records the authorised SQL application and preserves that service source while excluding its newer provider-binding update.

Errors are fixed codes without raw upstream text: disabled/unavailable 503, unauthenticated 401, insufficient scope/forbidden/inactive connection 403, inaccessible object 404, invalid/excessive input 400, rate limit 429. Each upstream call has a five-second response timeout. Membership, grant, subscription, token expiry and freshness are rechecked after reads. Audit records contain only operation/outcome and hashed user/business identifiers; inputs, tokens, guest identities, financial amounts and customer notes are excluded. Results are not cached, and the route sends `Cache-Control: no-store`.

## Security and consent release blockers

The existing closed read route and default service constant remain disabled. Only the new trusted server adapter can supply a validated restricted gateway and enabled provider configuration; request fields cannot do so. Both environment and private DB switches plus named pilot lists are required. Muse is hard-disabled independently. Production routes import no test fixtures.

The separately recorded 3 October release applied foundation migration `20261003160000_agent_read_foundation`, with disabled defaults, RLS, invoker aggregate functions, restricted grants and zero grants at verification. The new private gateway/issuer/role-change schema extension is still local and outside the migration ledger. Rehearse it against the actual applied foundation; do not recreate that table or reapply the foundation migration in production. This implementation pass ran no production SQL.

Native Supabase sign-in remains authoritative for consent and disconnect. Opaque MCP tokens are separately scoped to one business/provider/client/resource/grant, last at most ten minutes and cannot extend the seven-day absolute consent period. PKCE, refresh rotation/replay revocation, atomic disconnect and sticky membership/role-change revocation are implemented locally. The connection page initiates no linking and shows consent only for a validated request. AI permission is separate from marketing consent.

The production gateway design uses bounded, parameterized private APIs under a non-bypass RLS owner, with no direct business-table privileges or service-role client. It reuses canonical reads and an atomic 30/minute user/business quota. Unexpected broad privileges reject access. Local PostgreSQL tests establish these properties in a synthetic schema; they cannot establish actual production catalog/pooler compatibility or every deployed native bypass entry point.

Remaining gates: actual schema/ACL review and restricted TLS credential; separate authorized SQL rehearsal/release; native sign-in/browser consent and REST/RPC/Edge/Admin token-confinement tests; actual HTTPS Inspector/ChatGPT journeys; independent Muse contract/test access; existing audit/lint findings and operational retention review. Passing these local tests does not resume wider qualification. See [the release handoff](mcp-implementation.md) and [security decision](mcp-security-decision.md).

## Acquisition outcomes and companion changes

`scripts/operator-acquisition-report.mjs` accepts an already authorized internal PostgreSQL client and an explicit set of 1–50 business UUIDs. It performs bounded reads in `BEGIN READ ONLY` with a five-second statement timeout and always rolls back. Date range is at most 31 days; each source is capped at 1,000 records. It has no environment loader, analytics SDK, automatic emitter, public endpoint or customer-table query. It is not an agent tool or a customer-facing permission boundary.

| Milestone | Authoritative evidence | Current coverage and deduplication |
| --- | --- | --- |
| Demo click | Consented website interaction | Unavailable in this application report; a click is not an account or payment |
| Lead submitted | Successfully accepted lead with a stable submission ID | Unavailable; submission success must be established by the receiving service |
| Operator account created | First successful operator Auth-account link committed with a durable event | Unavailable. Current MAIN_ADMIN membership and Auth `created_at` can reflect migrations, reused accounts or role changes and are deliberately not counted |
| Trial activated | Actual recorded transition into TRIAL | Only explicit business status audit transitions can project this event; current TRIAL/ACTIVE or setup completion cannot. Complete trial-emitter coverage was not established. Key: event type plus business UUID |
| Operator subscription payment confirmed | Reconciled PAID/YOCO `platform_invoices` row with positive recurring/total amount, provider reference and paid timestamp | Projects recorded invoice confirmation; manual marks and traveller payments are excluded. Key: event type plus invoice UUID. Repeated monthly invoices are payments, not new acquired businesses. Invoice rows do not establish provider test/live environment: outputs explicitly use `payment_environment: unknown` and `live_conversion_confirmed: null`. Settlement was not checked |

Every projected outcome keeps source `unknown` until a consented cross-repository attribution join exists. `acquisitionAttribution` accepts only coarse allowlisted tags and operator-acquisition analytics consent; exact `chatgpt.com` normalizes to `chatgpt`. A tag is labelled `campaign_tag`, not proof that a platform referred or recommended the product. Lookalike domains, arbitrary URLs, contact details, tokens and unapproved campaigns are discarded. The helper is tested but not wired into an intake flow. Existing traveller cookie-notice dismissal and booking marketing choices do not establish operator analytics consent.

Companion website work: define a shared approved campaign allowlist; retain coarse attribution after explicit analytics consent; separately record demo clicks and accepted leads; and attach a random opaque submission/reference ID to a coordinated intake handoff. Use a server-side mapping rather than putting contact details or credentials in URLs. Application work: persist an immutable first operator-account-link event, establish trial activation coverage and join authorized intake records to a business. Separate deployments must not assume shared cookies/storage. Deduplicate outcome keys in the eventual consumer, distinguish recurring payment events from first paying businesses, and preserve withdrawal/retention behavior. None of those live flows is claimed implemented here.
