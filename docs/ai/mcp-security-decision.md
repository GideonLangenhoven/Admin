# MCP credential and database boundary

Decision date: 3 October 2026; verification continued 4 October. Status: implemented and tested locally with synthetic identities/data; production architecture acceptance remains pending. This implements the security spike in the [build plan](mcp-chatgpt-muse-build-plan.md). It does not authorize a migration or deployment.

Use dedicated opaque MCP credentials rather than exporting the operator's normal Supabase session. Supabase Auth remains the identity authority for operator consent and disconnection: the server validates the supplied native session through `auth.getUser`, using the existing public key. No Supabase session, service-role key, password or signing key is stored by this integration or sent to an agent.

The established `@node-oauth/oauth2-server` library implements authorization-code exchange, S256 PKCE and rotated refresh credentials. Random credentials contain 256 bits of entropy. The database receives only SHA-256 credential/ticket hashes. Access credentials expire within ten minutes, codes within sixty seconds and grants within an absolute 168 hours. Refresh cannot extend a grant. Refresh replay revokes the grant and its whole token family. An incorrect PKCE verifier consumes the code; start a new authorization request.

The Node server uses a separate PostgreSQL gateway credential. The gateway has no direct business/private-table permissions, no application/service/owner role membership, no inheritance and no RLS bypass. It may execute only the finite private `store` and `read` APIs. Their non-login, non-bypass owner has explicitly bounded column reads, agent-state writes and dedicated RLS policies. The policies apply only to that role; restrictive policies also constrain pre-existing policies granted to PUBLIC. Native Supabase users' policies and permissions are preserved.

Every data action validates the opaque credential's expiry, provider/resource/client/grant/scopes and current Auth identity, owner membership, suspension, read-only status and business eligibility. Object ownership is checked again in SQL. A membership-change trigger revokes only the affected agent grants/tokens when user, business, role, suspension or read-only status changes or membership is deleted. Restoring a role cannot revive old consent; native business rows and permissions remain unchanged. The private helper sets transaction-local database identity context solely for existing invoker RLS/functions. This context is not a signed JWT and cannot be used at Supabase REST/RPC/Edge or Admin endpoints. Pooled connections do not retain it beyond the transaction.

The finite gateway implements the existing shared service's read vocabulary. Capacity comes from the existing `slot_available_capacity` function; payment attention retains `amountOutstanding`; participant attention uses the existing aggregate candidate. No booking, capacity, billing, payment, refund, waiver signing or messaging rule is reimplemented. Waiver evidence stays inside the restricted aggregate function.

The server verifies the gateway role before each request. Unexpected direct table access or executable SECURITY DEFINER functions cause `INTEGRATION_DISABLED`. Existing PUBLIC grants on legacy definer RPCs are therefore a release blocker until a catalog/ACL review can deny the new gateway while preserving native callers. The candidate does not mass-rewrite those existing privileges. The local test grants legacy functions explicitly to their native callers and removes PUBLIC execution only in its disposable fixture database.

Queries are parameterized and fixed; no dynamic SQL, URL proxy, arbitrary table selector, service-role business client or tenant-wide enumeration exists. Reads use an atomic user/business quota, no cache, bounded queries and post-read authorization. OAuth, metadata/transport and connection management have shared bounded abuse quotas. Security-state writes are limited to consent, issuance, revocation, quota bookkeeping and cleanup; business-state writes are absent.

Expired requests/codes and absolutely expired refresh-token hashes are removed opportunistically in batches of at most 100 during new request/token issuance. Live refresh hashes remain until absolute expiry for replay detection. Client registration and connection/audit metadata require a reviewed operational retention policy before customer launch; there is no new cleanup cron or marketing use of this state.

Agent-route and consent-page Sentry errors, transactions and breadcrumbs are suppressed. Application audits use fixed action/outcome labels and optional hashed identity references, without credentials, URLs, arguments, customer records or raw upstream errors. MCP codec errors are also redacted on both JSON and SSE responses.

## Evidence and remaining acceptance gate

Real local PostgreSQL, RLS, OAuth library and MCP SDK tests exercise two synthetic tenants, PKCE/code reuse, refresh rotation/replay, expiry, scope/object isolation, disconnect, role/membership/identity/business changes, distributed quota failure, private-field exclusions and unchanged domain state. Both SDK protocol formats are exercised in process. Native JWT parsing locally rejects the opaque credential; the gateway denies direct table writes and private state access.

Operator identity is injected in the positive OAuth/backend fixtures. Seven separate [native Auth checks](mcp-native-auth-rehearsal.md) passed against official local Supabase Auth with a synthetic account, including positive native sign-in and identity deletion. These establish local identity validation only; they do **not** prove browser login/MFA/consent, deployment-pooler compatibility or rejection by every deployed REST/RPC/Edge/Admin entry point. Before activation, provision a restricted staging credential and review real table/RPC/RLS/ACL ownership, then test real native sign-in and every bypass entry point. Stop if native user permissions change. No ordinary operator session should be revoked when disconnecting an MCP grant.

ChatGPT uses HTTPS protected-resource/issuer discovery, authorization code with S256 PKCE, DCR public clients (`none`) and exact registered redirects. Per-tool OAuth declarations appear both at top level and in `_meta`; reauthorization challenges include discovery and a fixed explanation. These follow [OpenAI's authentication contract](https://developers.openai.com/plugins/build/auth). Client ID Metadata Documents are not supported or fetched by this implementation.

Muse remains a separate closed track. Its public [connector guidelines](https://muse.ai/platform/docs) permit read-only account reports and require independent review. They do not supply the precise BookingTours transport/client/authentication contract. No ChatGPT credential, SDK or manifest is treated as evidence of Muse compatibility.
